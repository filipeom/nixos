## Context and Problem Statement

The homelab has grown organically around a flat home network and a single
public entry point. Services, data, and compute are mixed across hosts of
different roles and hardware classes. There is no formal model for what each
machine is for, where data lives, or how external traffic reaches internal
services.

Current state:

- **Flat network:** everything sits on `192.168.1.0/24` behind the ISP router
  (`192.168.1.1`). There are no VLANs and no dedicated firewall/router node.
- **Edge migrated:** the public entry point moved from `anchor-01` to
  `vessel-02` in 2026-10. `vessel-02` runs nginx on `:443`, terminates TLS with
  ACME (DNS-01 at OVH), updates OVH dynamic DNS with `ddclient`, and serves
  unbound DNS for the LAN.
- **Anchor is internal-only:** `anchor-01` now runs NixOS (flake host
  `anchor-01`) as the data host — Nextcloud 34, Plex, MariaDB, and the ZFS
  pools. It exposes no public listener; nginx on `:80` and Plex on `:32400`
  serve the edge over the LAN.
- **Vessels are compute:** `vessel-01` (NixOS desktop) and `vessel-02` (NixOS
  server) run workloads; `vessel-02` is the active edge and runs the WireGuard
  server (`10.100.0.1`) plus the GitHub runner and Minecraft.
- **Management plane:** remote deploys to the vessels use direct LAN access
  (`vessel-0N.local`); the `ProxyJump=anchor-01.filipeom.dev` dependency was
  removed from the `Makefile` on 2026-10-01 (off-site access is via WireGuard).
- **Uniform platform:** all hosts run NixOS 26.05 and are declaratively managed
  from this flake; `cflinux` is home-manager only.
- **Residential connectivity:** dynamic public IP, managed via OVH DNS
  (`ddclient` on `vessel-02`, record `vessel-02.filipeom.dev`). See
  [RUN-002](RUN-002.md).
- **Observability pending:** the Ubuntu-era Docker stack (Prometheus, Grafana,
  node-exporter in `~/projects/monitoring`) was retired with the migration and
  is not running. `scripts/check-host.sh` is the only in-repo check. Migrating
  to native NixOS modules is tracked in [FS-001](FS-001.md).
- **Power:** a Salicru One 1100VA UPS feeds the rack, USB-attached to
  `anchor-01`. After the NixOS migration NUT is not configured at all, so no
  host receives UPS state or shuts down gracefully on battery; re-implementation
  is tracked in [FS-001](FS-001.md).
- **Hardware:** a 27U rack with 10U used / 17U free. See [INV-001](INV-001.md).

## Scope

- **In scope:** the rack hosts (`anchor-01`, `vessel-02`), `vessel-01` (desk
  machine, architecturally managed), the network hardware (ISP router, switch),
  and the UPS.
- **Out of scope:** `helm` (personal laptop; only a WireGuard client) and
  `cflinux` (work machine, home-manager only). They may appear as peers or SSH
  origins but are not part of the homelab architecture.
- **Explicit non-goals:** backup/restore design (planned ADR-002; until it is
  accepted, the stopgap is manual restic snapshots of configs and
  irreplaceable data to external/offsite media), secrets tooling selection,
  public IPv6 service exposure, and detailed observability stack sizing (that
  belongs in a future spec or the planned `INV-003` services inventory).

## Requirements and Decision Drivers

1. **Anchors must not be reachable from outside the network.** Data/stateful
   services should only be reached indirectly through a controlled ingress.
2. **Expansion in mind.** Adding compute, storage, or a new ingress point should
   be a repeatable, low-ceremony operation.
3. **Low operational burden.** Prefer solutions that scale to a homelab, not an
   enterprise. Avoid infrastructure whose maintenance cost exceeds its value.
4. **Declarative where possible.** NixOS hosts should be configured from the
   flake; avoid undocumented manual state.
5. **Security proportional to exposure.** Public entry points are the highest
   risk surface and must be the most hardened, most isolated tier.

## Terminology: Architecture Tiers

| Tier | Purpose | Hosts today |
|------|---------|-------------|
| **Network** | Routing, switching, firewall, segmentation. | ISP router; TP-Link TL-SG105E switch |
| **Edge** | Public entry point. Terminates external client connections, reverse-proxies to internal services. | `vessel-02` (active)*, `vessel-01` (standby) |
| **Anchor** | Core data and stateful services. Internal-only. | `anchor-01` |
| **Compute** | Stateless/elastic workloads (game servers, CI runners, containers). | `vessel-01`, `vessel-02` |
| **Management / Observability** | Internal monitoring, metrics, logs, alerting, and UPS state. | `anchor-01` (co-located) |

> \* With a single WAN IP, at most one host holds the `:443` port-forward at a
> time. `vessel-02` is the always-on active edge; `vessel-01` is a standby edge
> that requires re-pointing the router's port-forward. `vessel-01` is also a
> desktop that hibernates, so its edge role is best-effort.

"Vessel" is used as the general-purpose node name in `vessel-NN`; the same
physical host may act as both **Edge** and **Compute**. Anchors are named
`anchor-NN`.

## Decision: Role Model

**Status: Current** — the ingress migration completed in 2026-10; `anchor-01`
is an internal service host and `vessel-02` is the active edge.

- External clients reach services through an edge vessel's nginx reverse proxy.
- Anchors are never exposed directly. All public ingress terminates on a vessel.
- `anchor-01` is internal-only; its nginx `:80` and Plex `:32400` listeners are
  reached only over the LAN by the edge.

*Accepted tradeoff:* `vessel-01` hibernates and is therefore not a reliable edge
node. This is accepted; `vessel-02` is the primary edge, and `vessel-01` serving
as an entry point is opportunistic. If edge availability becomes important, a
dedicated always-on edge host should be introduced (see
[Expansion Playbook](#expansion-playbook)).

## Decision: Management Plane

**Status: Partially implemented.**

- Administrative access to hosts must not depend on a service that is publicly
  exposed on an anchor.
- On 2026-10-01 the `ProxyJump=anchor-01.filipeom.dev` dependency was removed
  from the `Makefile`; remote deploys now use direct LAN access
  (`vessel-0N.local`) from this network. A documented off-site path (WireGuard)
  is still a committed follow-up.
- SSH on anchors is not port-forwarded; the public surface is HTTPS on the
  active edge only.

## Decision: No Load Balancer

An external request should be routed **by hostname**, not balanced.

Rationale: a load balancer distributes the *same* service across replicas. The
homelab hosts *distinct* services, so there is nothing to balance. Introducing a
load balancer between the edge nodes would add a hop, a failure mode, and
configuration overhead for no benefit.

**Target request flow:**

```
external client
      │  (DNS: service.filipeom.dev)
      ▼
ISP router ──port-forward :443──▶  vessel-02 (active edge: nginx, TLS)
                                        │  (internal hostname)
                                        ▼
                                  anchor-01 (internal listener / service)
```

- If `vessel-02` fails, failover means re-pointing the router's `:443`
  port-forward to `vessel-01`. DNS and certificate material do not change, so
  failover is a single router change, not a migration.
- Both edges must have valid certificates at all times (see below).

If high availability is later required, the options are:

1. **VRRP floating VIP** — `keepalived` + nginx on both edges, sharing a
   virtual IP that the ISP router forwards to. Adds automatic failover without
   a dedicated balancer and without router changes.
2. **Cloudflare Tunnel** — `cloudflared` connectors on multiple hosts;
   Cloudflare provides edge TLS, load balancing, and origin hiding with no open
   ports. This implies moving `filipeom.dev` DNS from OVH to Cloudflare and is
   a larger decision (would warrant its own ADR).

Neither is adopted now.

## Decision: Ingress and TLS

**Status: Current** — `vessel-02` runs nginx, ACME (DNS-01), and `ddclient`
today.

- nginx + ACME run on the edge vessels and terminate public TLS on `:443`.
- `vessel-02` is the active edge; `vessel-01` is the standby (see
  [No Load Balancer](#decision-no-load-balancer) for failover).
- `ddclient` (OVH dynamic DNS) is a property of the **edge**; it now runs on
  `vessel-02` and updates `vessel-02.filipeom.dev`.
- The edge reverse-proxies by `server_name` to internal hosts over the LAN.
- **ACME challenge:** implemented via **DNS-01 at OVH** (`security.acme` with
  the OVH provider). It removes the need to forward `:80`, works for hosts that
  are not the active edge, and allows wildcard certificates. HTTP-01 is
  acceptable only if `:80` is forwarded to the active edge.

**Double-proxy today:** `anchor-01` still serves its own nginx for Nextcloud, so
requests traverse `vessel-02 nginx → anchor-01 nginx :80 → service` (Plex is
proxy-passed directly to `:32400`). This is acceptable transitional complexity;
the target is a single edge proxy layer with anchors exposing plain internal
listeners.

**Edge hardening expectation:** edge nodes run the minimum required services,
are patched promptly, and host no user sessions or unrelated workloads. The
vessels currently violate this (desktop stacks, Ollama, podman, CI runner,
Minecraft, WireGuard NAT); this is an **accepted risk** until a dedicated edge
node exists (see [Expansion Playbook](#expansion-playbook)).

Follow-up work (not in this ADR): implement the edge proxy declaratively as a
shared NixOS module (e.g. `modules/services/edge-proxy.nix`) so
`vessel-01`/`vessel-02` share one configuration. See [RUN-001](RUN-001.md) for
the current manual procedure.

## Observability and Monitoring

**Decision: the observability backend is an internal service hosted on
`anchor-01`.**

Current reality: the Ubuntu-era Docker stack (Prometheus, Grafana,
node-exporter; compose at `~/projects/monitoring`) was retired with the
`anchor-01` migration. The native replacement is partly deployed on
`anchor-01`: Prometheus (90d retention) scraping the node and NUT exporters,
and Grafana with provisioned datasources/dashboards. On 2026-10-08 Loki (30d
retention) was added, with Grafana Alloy on `vessel-02` shipping nginx, sshd,
and fail2ban logs enriched with GeoIP (DB-IP Lite) — see
[RUN-003](RUN-003.md). Alertmanager, the off-host uptime probe, and restoring
the archived Grafana data are still tracked in [FS-001](FS-001.md).

Scope:

| Concern | Tooling |
|---------|---------|
| Metrics | Prometheus + `node_exporter` (and per-service exporters) |
| Dashboards | Grafana |
| Logs | Loki + Alloy/Promtail collectors |
| Uptime | Uptime Kuma (off-host probe — see below) |
| Power / UPS | NUT exporter against `anchor-01`'s NUT server |
| Alerting | Alertmanager → outbound notification channel |

**Data flow:**

```
exporters/agents (all hosts)
        │  scrape / push (LAN only)
        ▼
anchor-01  ── Prometheus + Loki ──▶ Grafana (dashboards)
        └── Alertmanager ──▶ outbound (email / ntfy / Telegram)
```

- The backend is **internal-only**, consistent with the anchor tier. Grafana is
  published through the edge reverse proxy with TLS and authentication (e.g.
  `grafana.filipeom.dev`); it is never port-forwarded.
- Scrape endpoints and the Grafana UI bind to the LAN; no monitoring port is
  exposed publicly.

**Coupled fate (accepted risk).** `anchor-01` is both the primary monitored
host and the host running the monitoring. If it fails, or the home link drops,
the monitoring fails with it. This is accepted for now, with two mandatory
mitigations:

1. A **separate, off-host uptime probe** (a small service on another host, or a
   hosted check) so that outages of `anchor-01` or the WAN are still detected.
2. An **outbound alert path** that does not depend on the anchor's services
   (e.g. the probe or an external check delivers the notification directly).

Metrics/logs during an anchor outage are lost until it returns; accepted for a
homelab.

**Storage and retention.** The Prometheus TSDB and Loki data live on
`anchor-01`'s 1TB NVMe (WD Black SN7100) with bounded retention. The HDDs remain
bulk storage; random-write time-series data does not belong on them. The stack
must be given explicit CPU/memory limits so it cannot compete with
Nextcloud/Plex on the smallest-RAM host.

**Declarative requirement.** `anchor-01` now runs NixOS, so the stack can be
implemented as native modules. Credentials (Grafana admin, alert delivery) must
be managed as secrets (sops/agenix) as part of that work.

Detailed stack versions, dashboards, and retention sizing are out of scope here
and belong in a future spec or the planned services inventory (`INV-003`).

## Decision: UPS Monitoring (NUT)

**Status: Target (pending re-implementation).**

After the NixOS migration NUT is not configured anywhere; the Ubuntu-era
standalone `upsd` on `anchor-01` is gone. Clients, netserver mode, and the
exporter are all pending ([FS-001](FS-001.md) Phase 4).

The UPS must trigger a **graceful shutdown** of UPS-backed hosts, and its state
must be visible to the observability stack.

**Topology:**

- **Server / primary:** `anchor-01` via USB (Salicru units typically use
  `nutdrv_qx` or `blazer_usb`; confirm with `nut-scanner -U`).
- **Clients (`netclient`, auto-shutdown):** `vessel-01`, `vessel-02`.
- The **switch and network gear are on UPS power**, so NUT clients can still
  reach `anchor-01` during an outage. `helm` and `cflinux` are not UPS-backed
  and are not clients.
- `upsd` listens on the LAN (`192.168.1.124:3493` and `127.0.0.1`) only, never
  port-forwarded, and the firewall permits `3493/tcp` from infrastructure hosts
  only.

**Shutdown semantics:** on low battery, clients shut down immediately; the
anchor (primary) delays its own shutdown (`FINALDELAY`) so the stateful services
stop last. A hibernated `vessel-01` needs no action.

**Indicative configuration** (setup steps are intentionally not a runbook yet):

```ini
# anchor-01, /etc/nut/ups.conf
[salicru]
  driver = nutdrv_qx
  port = auto
```

```nix
# vessel-01 / vessel-02 (NixOS power.ups module)
power.ups = {
  enable = true;
  mode = "netclient";
  upsmon.monitor = [ "salicru@192.168.1.124 1 upsmon <PASSWORD> secondary" ];
};
```

**Accepted debt and risks:**

- `anchor-01` is NixOS now, so the NUT server can be declarative; until it is
  re-implemented there is no graceful UPS shutdown at all.
- NUT is plaintext with a shared credential; LAN-only binding and firewall
  rules are the only protection today. The planned `mgmt` VLAN (see
  [Migration Path](#migration-path-to-router--vlan-segmentation)) is its
  long-term home, and the credential should move to sops/agenix.
- The NUT server is a single point of control: if `anchor-01` hangs, clients
  receive no shutdown signal. Clients must alert on losing the NUT connection.
- Measured load/runtime from NUT will finally answer the power open question in
  [INV-001](INV-001.md).

## Addressing Plan

Policy (this ADR) is separated from the live allocation table (future
`INV-002`, network addressing).

**Current state (illustrative):**

| Host | IPv4 | IPv6 (ULA) | Notes |
|------|------|------------|-------|
| gateway | `192.168.1.1` | — | ISP router |
| `anchor-01` | `192.168.1.124` | — | internal anchor; Nextcloud/Plex; nginx `:80` |
| `vessel-01` | `192.168.1.110` | `fd00::110/64` | desktop/compute |
| `vessel-02` | `192.168.1.111` | `fd00::111/64` | active edge; unbound DNS; `ddclient`; WireGuard server |
| WireGuard | `10.100.0.0/24` | `fd00:100::/64` | server `10.100.0.1`; peers include out-of-scope clients (e.g. `helm`, `10.100.0.10`) |

**Rules and reservations:**

- Reserve `192.168.1.100–199` for infrastructure static assignments;
  `.200–254` for DHCP leases.
- Static configuration on servers; no DHCP for infrastructure hosts.
- Server hostnames resolve as `<host>.local` via mDNS/Avahi on the LAN.

**Future (when segmentation is adopted):** move to a `10.x` scheme with VLANs
(see [Migration Path](#migration-path-to-router--vlan-segmentation)).

## Expansion Playbook

**Add a compute node (vessel):**
1. Assign the next free static IP from the infra reservation; add it to the
   flake as `hosts/vessel-NN/` and to `nixosConfigurations`.
2. Attach to the switch, confirm `make check` / `reboot-*` tooling reaches it.
3. Add DNS/IP entries to the addressing inventory and, if it serves HTTP, the
   edge proxy config.
4. If it is on UPS power, add it as a NUT `netclient`.

**Add an anchor:**
1. Same as above, plus: place it in the internal tier only (**never**
   port-forwarded).
2. Document its data location and backup posture.

**Promote a node to edge:** only if it is always-on. Edge nodes must not
hibernate; a hibernating desktop may still be a best-effort edge but cannot be
the primary. The node must accept the edge hardening expectations above.

**When to introduce a dedicated edge host:** when edge availability matters, or
when the edge nodes' primary role (compute/desktop) conflicts with reliable
ingress.

- Candidate on hand: an **i7-3770 / 16 GiB** machine. It is powerful enough for
  a reverse proxy, but it is 2012 hardware with higher idle power than a modern
  N100-class mini-PC; evaluate power, noise, and reliability before committing.
- If two permanent edges exist, `keepalived` VRRP provides automatic failover
  without router changes and is then the preferred HA mechanism.

## Migration Path to Router + VLAN Segmentation

**Prerequisites (not yet satisfied):**

- **Internal DNS:** `.local`/Avahi does not cross VLANs. A LAN DNS service
  (e.g. unbound/dnsmasq) must exist before segmentation, and it also removes
  the `/etc/hosts` entries currently used for internal name resolution.
- **Switch check:** the TP-Link TL-SG105E is 802.1Q-capable, but it is a 5-port
  Easy Smart switch. Verify trunk and per-VLAN behaviour and the port budget
  before relying on it.
- **Router placement:** decide whether the router is a dedicated node
  (NixOS router or OPNsense) or software on an existing host, and which tier it
  lives in.

**Triggers (any of):**

- Anchors and vessels need a *network-enforced* boundary, not just host config.
- The flat subnet approaches its reservation limits or DHCP conflicts occur.
- A dedicated firewall/routing feature is needed (inter-VLAN rules, a stable
  VIP/gateway for WireGuard, traffic inspection).

**Target topology:**

| VLAN | Purpose | Members (examples) |
|------|---------|--------------------|
| `10` mgmt | Out-of-band admin, switch/UPS/NUT | management endpoints, `anchor-01` NUT |
| `20` DMZ | Edge/vessels (exposed) | `vessel-01`, `vessel-02` |
| `30` trusted | Anchors/data + clients | `anchor-01`, workstations |

**Cutover (outline):** create VLANs on the switch → build the router node and
firewall matrix (allow edge→anchor on service ports only; deny anchor egress to
the internet except updates; deny any inbound to anchors) → stand up internal
DNS → move hosts one at a time → update the addressing inventory and DNS →
decommission flat addressing.

## Threat Surface and Security Model

- **Public surface:** `:80`/`:443` on the active edge (`vessel-02`) only.
  `anchor-01` no longer receives public traffic and has no public name.
- **Edge hosts** are the highest-risk tier: minimal services, prompt patching,
  no user sessions, no unrelated workloads. Current vessels do not meet this;
  accepted until a dedicated edge exists.
- **Admin paths:** WireGuard is the preferred remote path; public SSH is
  removed from the target state.
- **Secrets:** sops/agenix once hosts are NixOS; until then (e.g. the NUT
  credential) secrets are manual and must be kept out of the repo.
- **Perimeter:** with a flat network, "anchors unreachable from outside" is
  enforced by host configuration, not by a network boundary. VLAN segmentation
  is the path to enforcement.
- **Edge abuse prevention:** fail2ban runs on the active edge (`vessel-02`)
  with the `sshd` and `nginx-botsearch` jails, incremental ban times, and an
  `ignoreIP` guard for the LAN and WireGuard ranges. Bans use the host's
  default iptables backend. Abuse is observable: the fail2ban Prometheus
  exporter on `vessel-02` and Loki/Alloy log pipelines feed Grafana dashboards
  including a GeoIP world map ([RUN-003](RUN-003.md)). Reverse-proxy rate
  limiting was considered and deferred; an `nginx-limit-req` jail can be added
  later without reworking this stack.

## Consequences

**Positive**

- Clear separation of data (anchors) from exposed ingress (vessels).
- No unnecessary load balancer; complexity matches service shape.
- A repeatable expansion path and a concrete segmentation upgrade when needed.
- A single internal observability tier (metrics, logs, uptime, alerting) without
  exposing any new public service.
- A UPS-shutdown design where clients stop first and the data host last, with
  UPS state observable and alertable (pending implementation).
- Management plane decoupled from the anchor's public name (direct LAN; an
  off-site WireGuard path is pending).

**Negative / costs**

- With a single WAN IP, only one edge is active; failover is a manual router
  change (no automatic HA).
- `vessel-01` edge role is unreliable due to hibernation, and both edge
  candidates are full desktops/servers rather than hardened minimal hosts.
- Observability and NUT are not deployed yet after the migration: there is
  currently no monitoring stack and no graceful UPS shutdown.
- Flat network means "anchors unreachable from outside" is currently enforced by
  configuration, not by a network boundary.
- Off-site management still needs a documented WireGuard path; the Makefile
  currently assumes LAN access.
- Observability is co-located with Plex/Nextcloud on `anchor-01`, the oldest and
  smallest-RAM host: resource contention, coupled fate, and a stack that is not
  yet deployed. Accepted, to be mitigated by an off-host uptime probe and an
  independent alert path.
- NUT credentials travel the LAN in plaintext and the NUT server is a single
  point of control for shutdown signalling.
- Backups are not covered by this ADR; until ADR-002, data is protected only by
  the manual stopgap.

## Alternatives Considered

- **Load balancer between edge nodes** — rejected; distinct services need
  hostname routing, not balancing.
- **VPN-only access (WireGuard/Tailscale), no public ingress** — rejected for
  public-facing services (Nextcloud/Plex); retained as a secure admin path.
- **Cloudflare Tunnel** — attractive (no open ports, built-in HA/origin hiding)
  but deferred; requires moving DNS to Cloudflare and is a separate decision.
- **Dedicated router node now** — deferred; documented as a migration path
  instead.
- **Hosted observability** (e.g. Grafana Cloud free tier) — removes coupled
  fate and operational burden, but sends telemetry off-site and adds an external
  dependency; rejected for now in favour of self-hosting.
- **NUT server on `vessel-02` instead of `anchor-01`** — rejected: the anchor is
  the host whose graceful shutdown matters most, it reboots least (`vessel-02`
  reboots for `make deploy-vessel-02`), and the UPS USB is physically attached
  there.
